Released: 21 October 2026

WarehousePG 7.6.1-WHPG is a security and maintenance release. It includes the following enhancements, bug fixes, and other changes:

::: info Note
WarehousePG 7.6.1 changes the privileges required to run some administration functions and views, and some existing clusters need follow-up SQL statements. Review [Upgrade considerations](#upgrade-considerations) before you upgrade.
:::

## Enhancements

-   ORCA now caches the interval constraint it derives from a constant `IN` or `NOT IN` list, which cuts planning time for long lists on partitioned tables. The new [`optimizer_array_interval_threshold`](../ref_guide/config_params/guc-list.md#optimizer_array_interval_threshold) configuration parameter limits the list length for which the constraint is derived at all.

## Bug fixes

-   Fixed ORCA losing rows from heap partitions, or from an external `DEFAULT` partition, when a partitioned table mixes external and heap partitions and a join on the partition key gives the dynamic scans a shared Partition Selector. Queries returned fewer rows than with the Postgres planner. Dynamic scans now match the selector's result to their partitions by OID.
-   Fixed every scan of a readable external table that has a `CHECK` constraint failing on the segments with `ERROR: unrecognized node type: 596`.
-   Fixed a crash when an append-optimized column-oriented scan is rescanned before it has returned a tuple, for example a `TABLESAMPLE` scan on the inner side of a nested loop.
-   Fixed `upper()`, `lower()`, and `initcap()` failing with `invalid multibyte character for locale` on non-ASCII text in a UTF8 database created with `LC_CTYPE=C` whenever the server runs under a UTF-8 locale such as `en_US.UTF-8`. Both the Postgres planner and ORCA were affected. The same change makes the validation of [`gp_resource_group_cgroup_parent`](../ref_guide/config_params/guc-list.md#gp_resource_group_cgroup_parent) check the whole value instead of its first 8 characters.
-   Fixed `gplogfilter` to correctly process the server's CSV logs. Several options, including `--tail`, `--trouble`, `-b`, `-e`, and `-d`, returned wrong results or failed since the Python 3 port. The `--prunefiles` option now skips log files outside the requested time range.
-   Fixed parallel worker startup for extension parallel index builds, such as pgvector's, which failed with snapshot and transaction errors when launched inside a PL/pgSQL loop or after a cursor.
-   Fixed `gpload` with `REUSE_TABLES`, `FAST_MATCH`, or `ERROR_TABLE` failing for non-superusers with `permission denied for view pg_exttable`. `gpload` now reads the `pg_exttable()` function, and `gp_exttable_fdw` 1.1 grants `SELECT` on the `pg_exttable` view to `PUBLIC`.
-   Fixed `orafce` `plvstr.normalize()` truncating its result at the first control byte in a multibyte database and returning repeated characters in a single-byte database.
-   Fixed the resource group cgroup detection to read `/proc/1/cgroup` line by line instead of with an unbounded `fscanf()`, which could overflow a fixed-size stack buffer when a cgroup path was longer than the buffer, and added the missing `NULL` check after `strpbrk()`.

## Security

-   Required `EXECUTE` on `pg_log_backend_memory_contexts(integer)` to call `gp_log_backend_memory_contexts()`, so any role can no longer make other sessions' backends dump their memory contexts into the segment logs, for [CVE-2026-104947](https://www.cve.org/CVERecord?id=CVE-2026-104947).
-   Restricted `gp_expand_lock_catalog()` and `gp_expand_bump_version()` to superusers, so any role can no longer call them, even with no `gpexpand` running, to block catalog changes or disconnect sessions that hold temporary tables, for [CVE-2026-104948](https://www.cve.org/CVERecord?id=CVE-2026-104948).
-   Restricted `gp_add_coordinator_standby()` and `gp_add_master_standby()` to superusers, so a regular role can no longer insert a standby row that blocks `gpinitstandby`, for [CVE-2026-104949](https://www.cve.org/CVERecord?id=CVE-2026-104949).
-   Restricted the `pg_backend_memory_contexts` and `gp_backend_memory_contexts` views and the `pg_get_backend_memory_contexts()` function to superusers and members of `pg_read_all_stats`, as PostgreSQL 14 and later do. See [Restricting the memory context views](#restricting-the-memory-context-views) for the required follow-up statements.
-   Raised the minimum TLS version for the `gpfdists://` external table client and the `s3://` protocol clients to TLS 1.2.

## Upgrade considerations

WarehousePG 7.6.1 changes the following behavior. Review each item before you upgrade.

-   A binary upgrade closes [CVE-2026-104947](https://www.cve.org/CVERecord?id=CVE-2026-104947), [CVE-2026-104948](https://www.cve.org/CVERecord?id=CVE-2026-104948), and [CVE-2026-104949](https://www.cve.org/CVERecord?id=CVE-2026-104949). `gp_log_backend_memory_contexts()`, `gp_expand_lock_catalog()`, `gp_expand_bump_version()`, `gp_add_coordinator_standby()`, and `gp_add_master_standby()` enforce their privilege inside the function. To give an upgraded cluster the same catalog privileges as a new one, optionally run the [REVOKE statements](#applying-the-function-privilege-changes-optional) in every database.
-   The `pg_backend_memory_contexts` and `gp_backend_memory_contexts` views and the `pg_get_backend_memory_contexts()` function are now restricted to superusers and members of `pg_read_all_stats`. `initdb` applies these privileges, so an upgraded cluster keeps `PUBLIC` access until a superuser runs the [REVOKE and GRANT statements](#restricting-the-memory-context-views).
-   `gp_log_backend_memory_contexts()` now requires `EXECUTE` on `pg_log_backend_memory_contexts(integer)`. To let a non-superuser role use it, grant that role `EXECUTE` on `pg_log_backend_memory_contexts(integer)` and on the `gp_log_backend_memory_contexts()` signature it calls.
-   The [`gp_exttable_fdw`](../admin_guide/external/external-tables/map_ext_to_foreign.md) extension is now version 1.1. Run `ALTER EXTENSION gp_exttable_fdw UPDATE;` in each existing database to let non-superusers read the [`pg_exttable`](../ref_guide/system_catalogs/catalog_ref-views.md#pg_exttable) view. `gpload` works without this step because it no longer reads the view.
-   The [`gp_toolkit`](../ref_guide/gp_toolkit.md#upgrading-the-extension) extension is now version 1.10. No post-upgrade step is required. To keep the extension version in step with the server, run `ALTER EXTENSION gp_toolkit UPDATE;` in existing databases whenever convenient. New databases get version 1.10 automatically.
-   External tables that use the `gpfdists://` and `s3://` protocols now require the remote endpoint to support TLS 1.2 or later. An S3-compatible store that only supports TLS 1.0 or 1.1 stops working.
-   The [`gp_resource_group_cgroup_parent`](../ref_guide/config_params/guc-list.md#gp_resource_group_cgroup_parent) configuration parameter is now validated in full at startup. A value with an invalid character after the eighth character, previously accepted, is rejected.
-   [`gplogfilter`](../ref_guide/utility_guide/reference/gplogfilter.md) `--prunefiles` now skips log files outside the requested time range, which it never did before, and flattened CSV entries end with `\n` instead of `\r\n`.
-   ORCA now plans `NOT IN (...)` lists that contain a `NULL` constant as a one-time false filter. Results are unchanged.

### Restricting the memory context views

After upgrading to 7.6.1, run the following as a superuser in every database of the cluster, including `template1` and `template0` (allow connections to `template0` for the duration). A binary upgrade doesn't change privileges already stored in the catalog, so without these statements `PUBLIC` keeps access to the views and the function:

```sql
REVOKE ALL ON pg_backend_memory_contexts FROM PUBLIC;
GRANT SELECT ON pg_backend_memory_contexts TO pg_read_all_stats;
REVOKE EXECUTE ON FUNCTION pg_get_backend_memory_contexts() FROM PUBLIC;
GRANT EXECUTE ON FUNCTION pg_get_backend_memory_contexts() TO pg_read_all_stats;
REVOKE ALL ON gp_backend_memory_contexts FROM PUBLIC;
GRANT SELECT ON gp_backend_memory_contexts TO pg_read_all_stats;
```

### Applying the function privilege changes (optional)

The 7.6.1 binaries already enforce these restrictions inside the functions. After upgrading, optionally run the following as a superuser in every database of the cluster to give the upgraded cluster the same catalog privileges as a new 7.6.1 cluster:

```sql
REVOKE EXECUTE ON FUNCTION gp_log_backend_memory_contexts(bigint) FROM PUBLIC;
REVOKE EXECUTE ON FUNCTION gp_log_backend_memory_contexts(bigint, bigint) FROM PUBLIC;
REVOKE EXECUTE ON FUNCTION gp_expand_lock_catalog() FROM PUBLIC;
REVOKE EXECUTE ON FUNCTION gp_expand_bump_version() FROM PUBLIC;
REVOKE EXECUTE ON FUNCTION gp_add_coordinator_standby(text, text, text) FROM PUBLIC;
REVOKE EXECUTE ON FUNCTION gp_add_coordinator_standby(text, text, text, integer) FROM PUBLIC;
REVOKE EXECUTE ON FUNCTION gp_add_master_standby(text, text, text) FROM PUBLIC;
REVOKE EXECUTE ON FUNCTION gp_add_master_standby(text, text, text, integer) FROM PUBLIC;
```
